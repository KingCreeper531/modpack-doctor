# Frozen contracts (M1)

These files are the shared contracts. **Only the integrator edits them.** A subagent that needs a
change writes a proposal in its report (what, why, which callers) and keeps working against the
current shape until the change is approved.

| Contract | Source of truth | Consumers |
|---|---|---|
| Rust ↔ TS data types | `src-tauri/src/model/*.rs` → generated `src/bindings.ts` | everything |
| IPC commands + events | `src-tauri/src/commands/mod.rs`, `src-tauri/src/lib.rs` (`specta_builder`) | `src/ui/app/ipc.ts` |
| IPC error shape | `src-tauri/src/error.rs` (`AppError`, `ErrorKind`) | UI error rows |
| Rules-core types | `src/core/model.ts` (`Finding`, `Evidence`, `Check`, `CrashPattern`, `JarIndex`, `VersionApi`) | `src/core/**`, UI |
| Path scoping | `src-tauri/src/guard/mod.rs` (`PathGuard`) | every Rust module that touches the filesystem |
| Jar id ↔ path | `src-tauri/src/jar_id.rs` | scanner, fix engine |
| App directories | `src-tauri/src/paths.rs` (icon cache, backups, API cache) | modrinth, fix |
| Test infrastructure | `src-tauri/src/test_support/mod.rs` (`JarBuilder`) | Rust tests |
| Design tokens and rules | `DESIGN.md`, `src/styles/tokens.css`, `src/styles/tailwind.css` | UI, reviewers |
| Dependencies | `src-tauri/Cargo.toml`, `package.json` | everyone (integrator adds crates) |
| Gates | `src/core/__tests__/purity.test.ts`, `src/ui/__tests__/design-lint.test.ts` | CI |

`src/bindings.ts` is generated by `cargo test --lib export_bindings` (also `npm run bindings`, and
every debug run of the app). Never edit it by hand. CI fails if regenerating it produces a diff.

## Invariants every agent must respect

1. **Rust owns all I/O.** The webview has no fs, dialog, store, shell or http permission.
   - Commands take ids and relative, `/`-separated paths, never absolute paths from the UI.
   - A relative path is joined with `PathGuard::join_relative`, then checked with
     `check_existing` or `check_new`.
   - Scope-bearing settings (manual folders, launcher roots) change only through the native-picker
     commands. `set_settings` takes a `SettingsPatch` that cannot express them.
   - Drag-and-drop is handled in Rust (`WindowEvent::DragDrop`) and reported to the UI as
     `InstanceAdded` or `DropRejected` events.
2. **Symlinks.** Discovery registers as PathGuard roots the instance root plus the canonical
   targets of its `mods/`, `logs/` and `crash-reports/` (one level). Everything else that resolves
   outside the roots is `OutsideScope`, except the read-only hs_err dirs (invariant 11), where
   `check_existing` accepts only `hs_err_pid<pid>.log` files and nothing is ever writable.
3. **`src/core` is pure.** No DOM, no Node, no `@tauri-apps/*`, only `import type` from
   `../bindings`, and no `any`. This is enforced by `purity.test.ts` and `tsc -p src/core`, which
   runs without DOM or Node libs.
4. **Rust extracts, TS interprets.** Version ranges cross the boundary as
   `RawRange { syntax, raw, unrepresentable }`, in OR-of-AND form. Rust may restructure Quilt
   objects into that form but never evaluates a range. Pack identity (including inference from the
   jar majority) lives in `src/core/pack`, so `src/core` chooses the Modrinth version for
   replace/install and passes a `versionId`.
   Range semantics are settled in `src/core/version`, so checks must not handle these cases
   again:
   - A bare Maven version (`47.1.0`) is a *soft* requirement and matches everything, as in FML.
     An empty restriction (equal bounds, at least one exclusive, e.g. `[1.0,1.0)`) is a parse
     error.
   - **Maven ranges are evaluated exactly like FML.** They use `ComparableVersion` on the raw
     strings, with **no** MC normalisation for either subject. So `pre` sorts *above* the release
     (`1.21-pre1` > `1.21`), while `rc` and `snapshot` sort below it. `compare(…, 'maven', …)` uses
     the same order. To order MC versions chronologically use `syntax: 'fabric'` with subject
     `minecraft`.
   - In Fabric ranges only the tested version is MC-normalised. Predicate versions stay as written,
     as in fabric-loader, so `>=1.20.5-pre1` does not match game `1.20.5-pre1`. A wildcard `X.Y.x`
     admits pre-releases, RCs and snapshots of `X.Y`.
   - Old-style `YYwWWx` snapshots after 2025, other than `26w14a`, don't normalise (`null`).
   - `satisfies` returns `null` (unknown, never a guess) for unparseable or unrepresentable input.
   - An unfilled build placeholder `${…}` in a range is evaluated as the loader does. FML (Maven
     3.8.5): a placeholder bound sorts below every real version (`[${x},)` = any, `(,${x})` = none,
     `[1.0,${x})` = parse error). Fabric: literal-string equality (no real version matches).
     `src/core/version/placeholders.ts` describes it; it is never displayed as a real requirement.
   - `Instance.loader = null` together with `metadataSource: 'launcher'` means a **vanilla**
     instance. `LoaderKind` has no vanilla member.
5. **IDs.**
   - Instance id = first 16 hex chars of SHA-1 over the canonical game dir path, lowercased on
     Windows and macOS. Discovery de-duplicates by it.
   - Top-level jar id = its path relative to the scan root with `/` separators and any
     `.disabled` suffix **stripped**, so it survives enable/disable: `mods/x.jar` for both
     `x.jar` and `x.jar.disabled`, or `client-overrides/mods/y.jar` in a `.mrpack`. If both
     `x.jar` and `x.jar.disabled` exist, the disabled one is `mods/x.jar#disabled`.
     `JarRecord.path` holds the actual file path. Build ids and resolve them back to files only
     with `src-tauri/src/jar_id.rs`.
   - Nested jar id = `<parentId>!/<entry path>`.
   - Log source id = its path relative to the game dir (`/` separators), or
     `@cwd/hs_err_pid<pid>.log` for a HotSpot crash log in the JVM's working dir when that is not
     the game dir (when a launcher runs the JVM outside the game dir). The `@cwd/` form is
     exact: a decimal pid with no leading zero, and nothing else. It names a file directly in a
     working dir that watch mode recorded for that pid of this instance, or, for vanilla
     instances, in the discovered `.minecraft` or a CurseForge `Install` hs_err dir when the file's `Command Line:` names the
     instance's `--gameDir`. The file must resolve inside a PathGuard root (invariant 2); nothing
     is registered for it. Only ids that `list_log_sources` returned are accepted. A malformed `@`
     id is `OutsideScope`, an unlisted one `NotFound`.
   - Backup id = `<instanceId>/<ms>`, validated as `^[0-9a-f]{16}/[0-9]+$`.
6. **Numbers.** Values that are `u64` in Rust are exported as TS `number` via
   `#[specta(type = specta_typescript::Number)]`, never `f64` (which exports as `number | null`).
   They are byte sizes and epoch milliseconds, always below 2^53.
7. **Errors.** Commands return `Result<T, AppError>`. `AppError.message` is a complete sentence a
   user can act on. `AppError.retryAfterS` is present only for `rateLimited` (seconds to wait). No `unwrap()`/`expect()` outside `#[cfg(test)]`.
8. **Fixes.**
   - The UI sends `FixAction` intents only. `plan_work_order` returns a stored `WorkOrder`, and
     `execute_work_order(id)` runs only stored orders.
   - Rust re-fetches every `versionId` from the API and re-validates it against the
     `PackIdentity` sent with `plan_work_order`. That identity must itself agree with launcher or
     mrpack metadata and any override. The checks:
     - `version.loaders` contains the pack loader (NeoForge 1.20.1 also accepts `forge`; Quilt
       also accepts `fabric`, since Quilt loads Fabric mods — decided 2026-11-07, matching
       `modrinthLoaders`).
     - `version.gameVersions` contains the pack MC version.
     - `Replace` stays within the same Modrinth project as the current jar, which must be
       identifiable by hash.
     - After download, the new jar must declare the expected mod id.

     Any failure rejects the order with a readable error naming the action.
   - Downloadable files exclude `fileType` `sources-jar`, `dev-jar`, `javadoc-jar` and `signature`.
     From what remains, pick the file marked `primary`, else the sole file, else planning fails
     with a readable error. "Sole file" counts the API's whole file list: when no file is primary
     and any file was dropped (`droppedFiles > 0`, off-CDN or hash-less), planning fails too. The
     TS `downloadFile` and the M6 planner apply this identical rule to the same `MrVersion`.
   - The URL must be `https://cdn.modrinth.com/…` exactly as the API returned it.
   - Every download is SHA-512-verified and written as temp file in the same dir → fsync → rename.
   - "Remove" moves the file into the backup snapshot; nothing is ever deleted.
   - Every order is refused while `game_running` reports true.
   - Undo is per action (`plan_undo(backupId, actionIndexes)`). It runs as a work order
     (`kind: undo`) and verifies hashes before it overwrites anything. Enter confirms only a
     single-rename undo; everything else needs Execute.
   - Update suggestions: `["release"]` unless `includeBeta`. If no release is compatible, or the
     newest compatible release is older than the identified version (a newer pre-release is
     installed), `src/core` retries with `["release","beta"]` for those hashes
     (`betaFallbackHashes`) and labels any result "beta". Alpha versions are
     never suggested. An update must be **published after** the identified version
     (`datePublished`): Modrinth returns the newest *matching* version, which can be older than a
     beta the user runs, and that is never offered (it would be a downgrade). When either date is
     missing the update is not offered.
9. **Minecraft versions** are no longer only `1.x.y`. Year-based releases such as `26.1`, `26.1.2`
   and `26.3`, and snapshots such as `26.4-snapshot-6`, are live, alongside legacy `1.21.11`,
   `23w51a` and `1.20.5-pre1`. Version code must never assume a `1.` prefix; use
   `VersionSubject = 'minecraft'`.
10. **Network.** The only hosts are `api.modrinth.com` (API) and `cdn.modrinth.com` (downloads
    and icons), GitHub for user-requested update checks (invariant 18), and `api.mclo.gs` for
    "Share on mclo.gs" only (below). Every request sends the User-Agent
    `KingCreeper531/modpack-doctor/<version> (github.com/KingCreeper531/modpack-doctor)`.
    Every static check works with no network.
    - (M5) One shared `ModrinthClient` lives in `AppState`. `Settings.modrinthEnabled = false`
      makes every Modrinth command cache-only (`offline: true`, no request); the change applies
      to the next command without a restart. Batched lookups never fail for network reasons
      (`failed` / `offline`); the UI shows `Modrinth unreachable — static checks only` then.
    - Icons are cached by Rust under `$APPCACHE/icons/` and shown with `convertFileSrc`; the
      webview never requests a remote URL. `modrinth_projects` never downloads icons (only cached
      ones are attached); `modrinth_icons` downloads them as a separate second pass, so Modrinth
      results never wait for the CDN. No icon request when Modrinth is off or unreachable.
    - Enrichment is pure TS in `src/core/modrinth` (frozen API in its `index.ts`): queries,
      `ModrinthContext`, beta-only fallback, per-jar match, the invariant-8 download file, and
      `replace` / `installDependency` fixes. `Finding.missingModIds` carries missing ids.
    - (E-DEP-RANGE advice) `src/core/modrinth/depRangeFix.ts`: `depRangeRequests` →
      `modrinth_resolve_mod_id` / `modrinth_project_versions` (pack filters, `["release","beta"]`) →
      `enrichDepRangeFindings`. It names the newest dependency version that is compatible, readable
      and satisfies every declared range on that dependency; else a dependent-mod version whose
      Modrinth dependencies name the installed version id; else says none matches. `replace` only
      under invariant 8 (identified by hash, same project, published after); downgrades are named
      as manual steps only. Never for `.mrpack`.
    - **mclo.gs.** `share_log(instanceId, sourceId)` uploads one log source that `list_log_sources`
      lists for that instance — read in Rust through the PathGuard, home folder replaced by `~`
      (same rules as invariant 16), cut to mclo.gs's limits (10 MiB / 25,000 lines) keeping the end —
      with one `POST https://api.mclo.gs/1/log` per explicit confirmation in the UI (which states the
      link is public). The webview passes only ids; no redirects are followed; the returned URLs are
      built from the returned id. The opener scope allows exactly `https://mclo.gs/*`. The "Look up
      mods online" switch does not apply. Pasted log text ("Paste a log") is analysed in TS only and
      never leaves the app or touches disk.
11. **Crash detection vs classification.** `src/core/crash/anchors.ts` (`CRASH_ANCHORS`) is
    the single, **tiered** anchor list. Each pattern marks every anchor `fatal` or
    `contextual` (`CrashAnchor` = `WatchAnchor`). The full list goes to `set_watch` with tiers,
    and its texts go to `read_log_digest`. (Owner decision 2026-11-03.)
    - **Fatal** anchors open an episode and notify promptly. They cover the crash report header,
      ResolutionException, "Missing or unsupported mandatory dependencies", Fabric's incompatible
      mod set (all wordings), FML "Mod loading has failed" / the NeoForge loading-error screen,
      the hs_err header and `#@!@# Game crashed!`. New crash-report and hs_err files are fatal too.
    - **Contextual** anchors (`Caused by`, mixin, NoClassDefFound, …) are recorded silently. They
      lead to analysis only if the instance's Java process exits within `CONTEXT_WINDOW_MS`
      (30 s), or a crash file appears.
    - Rust watch mode detects only. It tails `latest.log` across log rotation, watches for new
      crash files, and tracks the Java process. Process detection is shared with the
      running-game guard (`src-tauri/src/process/`, built in M4, reused by M6). It records each
      Java process's working dir and, on exit, treats `<cwd>/hs_err_pid<pid>.log` as a new hs_err
      file (fatal) when the PathGuard accepts it. It resolves `latest.log` through the PathGuard
      before each read. Only `crash-reports/crash-*.txt` are crash reports.
    - After an emission, triggers are suppressed until every Java process that was running at
      emission has exited (plus a 5 s grace); without process tracking, for a fixed 60 s. Nothing
      dropped during suppression extends it. A new crash file after the coalesce window opens a
      new episode.
    - The full episode rules are in `model/logs.rs`. They emit one `CrashDetected` per crash. A
      normal quit emits nothing; a normal quit is a process exit with no fatal event and no
      contextual hit inside the window.
    - The UI classifies the episode's `source` with `src/core` and sends a native notification
      only for an error-severity crash finding.
    - Rust never starts watchers by itself. The UI re-arms `Settings.watched` after every
      discovery load, for watched instances that are present and not already armed.
    - Known gaps (M4): a JVM that fails before logging starts (wrong Java, a LinkageError on the
      main class, bad JVM arguments) writes only to stderr and may live less than one poll, so it
      usually emits nothing. hs_err files in a working dir outside every PathGuard root (a
      vanilla `.minecraft` that no profile uses) are not read.
    - **CurseForge hs_err (owner decision 2026-11-07, done in M6).** Evidence (`launchers.md` §3):
      current CurseForge runs the JVM in the instance folder, so hs_err files land in the game
      dir. As a defensive measure, PathGuard has a read-only hs_err rule for the shared
      `<root>/Install` folder of discovered CurseForge instances (`set_hs_err_dirs`, re-set on
      every discovery, empty without CurseForge instances). It is not a root. `check_existing`
      accepts only regular `hs_err_pid<pid>.log` files directly in it, symlinks resolved, and
      `check_new` never accepts anything there. Files are attributed by the `--gameDir` in their
      `Command Line:` and listed as `@cwd/hs_err_pid<pid>.log`; files naming no known instance are
      ignored. Watch mode reads `<Install>/hs_err_pid<pid>.log` on exit when that is the recorded
      working dir.
    - Required tests: in M2 (TS), the tier marking itself. In M4, the Rust episode state machine
      with an injected clock and process source:
      - a healthy `latest.log` full of logged exceptions (contextual hits, game keeps running or
        exits normally after the window) produces **no** `CrashDetected` and no notification;
      - a load-time failure that appears **only** in `latest.log`, followed by process exit,
        produces **exactly one**.
12. **NeoForge/Forge.**
    - `ModMeta.loader` decides per entry. A `neoforge` dependency means NeoForge; a `forge`
      dependency, or neither, means Forge.
    - `languageRange` (`loaderVersion`) is an FML/language-loader range and is never compared with
      the Forge or NeoForge version. `loaderRange` is the range of the dependency on the loader mod.
    - NeoForge 1.20.1 counts as Forge 47.x-compatible.
    - A jar that ships both `neoforge.mods.toml` and `mods.toml` yields two `ModMeta` with the
      same `modId` and different `loader`. E-DUP-ID must ignore duplicates within one jar.
    - NeoForge `config/fml.toml` `dependencyOverrides.<mod> = ["-dep"]` removes every constraint of
      `<mod>` on `dep` (including `minecraft` and `neoforge`) from FML's dependency check. It exists
      from NeoForge 21.1.81 (1.21.1), 21.3.41-beta (1.21.3) and in all 1.21.4+ and 26.x builds, never
      on Forge, and never affects Fabric mods loaded through Connector. E-MISSING-DEP, E-DEP-RANGE,
      E-MC-RANGE, E-LOADER-RANGE and E-INCOMPAT findings it removes are reported at **info**,
      "overridden in config/fml.toml". `+dep` changes nothing.
    - Instance config files: after scanning an instance (not a `.mrpack`), Rust reads
      `config/fml.toml` and `config/connector.json` under the game dir (`PathGuard::join_relative` +
      `check_existing`; regular file ≤ 256 KiB, UTF-8). A missing file is absent; any other problem
      is a `ScanIssue` with the relative path as subject, never a failed scan. Raw facts go in
      `ScanResult.loaderConfig` (optional); `src/core` interprets them.
    - Sinytra Connector's alias groups come from `connector.json` `globalModAliases`; the defaults
      (cloth_config ↔ cloth-config2, playeranimator ↔ player-animator) apply with no file, or with
      an invalid file on 1.21.x; a readable file without the key means no aliases. `hiddenMods` has
      no static effect.
13. **Known model gaps** (accepted for now; revisit when a check needs them):
    - (Not a gap any more, for reference) Legacy Forge (MC < 1.13): the scanner reads class-level
      `@Mod` (`net.minecraftforge.fml.common.Mod`, 1.7.10 `cpw.mods.fml.common.Mod`) from top-level
      jars without 1.13+/Fabric/Quilt metadata (coremod/tweaker jars only with
      `FMLCorePluginContainsFMLMod`). Each yields a `legacyforge` `ModMeta` with `metadataFile` = the
      class path, merged with the `mcmod.info` entry of the same id: name from `mcmod.info`; version,
      `dependencies` and `acceptedMinecraftVersions` from the annotation (dependencies from
      `mcmod.info` only with `useDependencyInformation: true`); `[1.12]`/`[1.12.1]` widened to
      `[1.12,1.12.2]` as FML does. `@API(provides)` ids become `provides` of the jar's entry; literal
      coremod `DummyModContainer` ids become their own entries. `metadataFilesRead` treats `.class`
      metadata files like `mcmod.info`. Ids computed at runtime are not seen.
    - Quilt "any of" dependency arrays become individually Optional dependencies, so a missing
      "one of A, B" is not reported.
    - `JarRecord.moduleName` comes from `module-info` or `Automatic-Module-Name` only. `src/core`
      derives the JDK automatic name from the file name when it is absent.

14. **Fix execution (M6; safety-critical).** Adds to invariant 8; on any doubt, refuse.
    - **Plan** (`plan_work_order`) never mutates anything. It resolves every jar id against a
      fresh stat of the instance's `mods/` (not the UI's scan), records per op its preconditions
      (source exists with the planned size + mtime + sha1; destination absent), re-validates every
      Modrinth version per invariant 8 (loader incl. NeoForge-1.20.1→forge and Quilt→fabric, MC
      version, same project for `Replace`, update published after the current version, download
      file rule) and fails the whole plan with a readable error naming the action. `Replace` and
      `InstallDependency` need Modrinth enabled and reachable (else `Offline`). `Manual`
      actions only add notes. A destination that already exists is refused, never overwritten.
    - **Orders** live in Rust memory only, are single-use, and expire 15 minutes after planning
      (`NotFound` "this work order expired — review the fixes again"). `discard_work_order`
      drops one. At most one order per instance executes at a time, and never while that
      instance is being scanned (`Conflict`).
    - **Execute** order: game guard (`game_running` true → `GameRunning`, nothing touched) →
      write the backup snapshot manifest → ops in plan order, each re-checking its preconditions
      right before it runs (any mismatch fails the op) → emit `OpStatus` per op (running, then
      done/failed/skipped). Downloads: CDN URL from the re-fetched version only, streamed to
      `mods/.<name>.<nonce>.part`, size cap, SHA-512 verified, the jar scanned and required to
      declare the expected mod id (replaced jar's id, or `InstallDependency.modId` incl.
      `provides`), then the replaced jar moved into the snapshot, then fsync + rename to `dest`.
    - **Rollback:** the first failed op stops the order; every completed op of that order is
      reversed in reverse order (renames back, files moved back out of the snapshot, created
      files moved *into* the snapshot under `created/`); remaining ops are `skipped`;
      `rolledBack: true`. A rollback step that fails is reported in its op message and the
      snapshot is kept so undo can still recover. Temp `.part` files are removed.
    - **Backups:** `<app data>/backups/<instanceId>/<created ms>/` = `manifest.json`
      (`BackupEntry` plus, per op, the sha1 of every file before and after) and `files/`
      (moved-out jars, original relative paths). Written before the first mutation, updated after
      each op. Nothing under `backups/` is ever deleted automatically. Nothing is deleted
      anywhere: "remove" and rollback move files into the snapshot.
    - **Undo** (`plan_undo`) is a work order like any other, per action, planned from the
      manifest. Each reverse op checks the current file's sha1 against the manifest's "after"
      value (or absence); a mismatch makes planning fail for that action with a readable error
      (the user changed the file since), never a silent overwrite. Executed undos are recorded
      in `undoneActions`.
    - **Game guard** (`game_running`): Java process match (cwd / `--gameDir`). On Windows, only
      when no process matched, a secondary probe that can never disturb the game: open the first
      `mods/*.jar` for `FILE_READ_ATTRIBUTES` only with full sharing (no read/write/delete access,
      so it takes no part in share-mode checks) and ask
      `NtQueryInformationFile(FileProcessIdsUsingFileInformation)` which processes hold it; any
      process other than this app means the game is running. Never request `DELETE`, read or
      write access and never use `share_mode(0)`: the JVM's `ZipFile` opens jars with
      `FILE_SHARE_READ | FILE_SHARE_WRITE` only, so such a handle makes the game's own open fail
      (measured in M6; the earlier DELETE-probe wording was wrong).
    - **Write-ahead and recovery (M6 safety review).** Before each mutation the manifest records
      the op as running plus every intended move (source, destination, `.part` name), fsynced; after
      it, the actual result. `BackupEntry.status`: `complete`, `rolledBack`, or `incomplete`
      (interrupted, or a rollback step failed). For `incomplete`, `plan_undo(id, None)` plans a
      recovery from the *actual* recorded file locations (snapshot `files/`, `created/`, `dest`),
      checking each file's sha1, so any interrupted or half-rolled-back order can be restored.
      A completed recovery of an interrupted *fix* sets the backup to `rolledBack` (files as before
      the order; nothing left to undo), unless it had to leave a created file in place because the
      user changed it since (a note names it; the backup stays `incomplete`). A broken *undo* is
      recovered on its own: reverted to the state right after the fixes when the files allow (else
      finished, with a note), never touching other actions, and the backup returns to `complete`.
      A recovery that fails part-way leaves it `incomplete`. Per-action undo is refused on
      `rolledBack` and `incomplete` backups. Copy temps for cross-volume moves are named in the
      write-ahead record and moved into the snapshot by recovery. Recovery takes its own lock, never
      the execution claim, and skips the manifest of an order that is executing. On Windows each
      write-ahead save flushes the manifest file and the snapshot folder before the step proceeds.
      Rollback steps are all-or-nothing per op (a Download whose replaced jar cannot be moved back
      keeps its new jar in place, so the state stays a consistent "applied"). On startup, leftover
      `mods/.<name>.<hex>.part` files named in an incomplete manifest are moved into its snapshot.
    - **No replacing renames.** Every move refuses an existing destination atomically
      (Windows `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING`; elsewhere hard link + remove of
      the source, or `renameat2(RENAME_NOREPLACE)` on Linux), not check-then-rename.
      `.part` files are created with `create_new`. Cross-volume copies keep mtime.
    - **One app process** (`tauri-plugin-single-instance`); closing the window while an order
      executes is refused with a native message until it finishes.
    - **Bound intents.** `InstallDependency.modId` must be a required dependency declared by an
      enabled top-level jar of the instance and not already provided (built-ins, `provides`, nested
      jars); the version's project must equal the project Rust itself resolves for that mod id
      (`resolve_mod_id`). `Replace` stays within the jar's own project. The planner fetches every
      version fresh from the API (no cache, no stale fallback); a failure fails the plan.
    - **Confirmation shows the source URL:** the download row shows host + size, and the full CDN
      URL as a detail line.
    - **Tests run only on temp-dir copies.** No test, smoke tool or manual check mutates a real
      instance unless the owner asks.
    - **UI:** every mutation goes through a work order shown in the panel (DESIGN §6.4), including
      the mod-table enable toggle (a one-op order). After an order executes, the instance is
      rescanned and Modrinth re-enriched.

15. **`.mrpack` (M7).** Opened packs are read-only, never extracted to disk, never mutated.
    - Opened by `pick_mrpack` (native file dialog, `.mrpack` filter) or by dropping a file on the
      window (`WindowEvent::DragDrop` → `InstanceAdded` or `DropRejected`). Only regular files ending
      in `.mrpack` (case-insensitive), at most 512 MiB. Opened packs live for the session only (not in
      settings), survive rediscovery, and are removed with `remove_manual_instance`.
    - PathGuard gains a read-only exact-file rule for each opened pack (like the hs_err rule): it
      is not a root, `check_existing` accepts exactly that file, `check_new` nothing.
    - `Instance`: `launcher: mrpack`, `root` = `gameDir` = the pack's absolute path, id from the path
      like other instances, `metadataSource: mrpack`, MC version and loader from `dependencies`
      (`minecraft`, `forge`, `neoforge`, `fabric-loader`, `quilt-loader`; unknown keys ignored).
    - `scan_instance` on a pack: reads `modrinth.index.json` (formatVersion 1, game `minecraft`,
      ≤ 8 MiB, ≤ 10 000 files) into `ScanResult.declared`, and scans every `.jar` under
      `overrides/`, `client-overrides/`, `server-overrides/` in memory as `JarRecord`s whose `relPath`
      is the path inside the zip. Zip safety: entries with `..`, absolute or drive paths,
      backslashes, NUL, or reserved names are skipped as `ScanIssue`s; total uncompressed bytes
      ≤ 2 GiB, compression ratio ≤ 200:1 per entry, ≤ 20 000 entries; symlink entries ignored. Index
      problems (bad JSON, wrong formatVersion, unsafe `files[].path`, missing hashes) are `ScanIssue`s,
      never a crash. No download ever happens.
    - `src/core` checks declared files with Modrinth data (identified by sha1, like jars):
      a version whose `loaders` exclude the pack loader → E-WRONG-LOADER; whose `gameVersions`
      exclude the pack MC → E-MC-RANGE; a required dependency project not among the declared or
      override files → E-MISSING-DEP, lowered to **warning** for declared files (Modrinth can't see
      every provider; Quilted Fabric API counts as Fabric API; dependencies of versions built for
      another loader family are skipped); a repeated `files[].path` → the last entry counts (what
      installers write) plus a `ScanIssue`; not identified → I-NOT-ON-MODRINTH; a `downloads` URL whose
      host is not in Modrinth's allowlist (`cdn.modrinth.com`, `github.com`,
      `raw.githubusercontent.com`, `gitlab.com`) → **W-MRPACK-DOWNLOAD** (warning). An override jar's required
      dependency counts as present when a declared `mods/` file for the pack side is that Modrinth
      project (slug = mod id, `-` ≡ `_`) or is named `<id>-<version>.jar`; while the pack declares
      mod files that can't be confirmed, its E-MISSING-DEP is a **warning** saying so (never "not
      installed"). Override jars
      get every static check. Packs never get fix actions and are never written. Their findings
      carry `packEdits` for a **fixed copy** instead (`src/core/packfix`): replace (only with a newer,
      compatible version of the same project) or remove declared files built for another loader or MC
      version; add a missing declared dependency; remove override jars that are wrong-loader,
      corrupt, missing a dependency at error severity, or duplicates.
    - `plan_pack_fix(instanceId, edits)` validates every edit against the opened pack (paths exist;
      an override entry is a jar directly in an override `mods/` folder) and fetches every version
      fresh, checked as in invariant 8: download-file rule, `https://cdn.modrinth.com/` URL, sha1 +
      sha512 + size, the pack's loader and MC version. Replace: same project (identified by sha1) and
      published after the identified version. Add (bound intent): only a project some kept file
      requires, never one already in the copy (identified declared files, other additions, override
      jar ids/provides or `resolve_mod_id`); unsure → warning; `env` from the project's sides or the
      requirer's. Path collisions are refused, letter case ignored. Every plan identifies the
      declared files with one batched lookup when Modrinth is on (failure only warns unless a
      Replace/Add needs it). The copy's index is capped at `MAX_INDEX_FILES`. Plans live in Rust
      with the pack's size/mtime/sha1: single use, 15 minutes, one per pack; a stale pack drops it.
    - `save_fixed_pack(planId)` opens the native save dialog (default `<stem> (fixed).mrpack`,
      `.mrpack` enforced) and refuses any opened pack as destination by **file identity** (volume
      serial + file index / dev + inode), re-checked right before a replacing rename. It copies every
      safe entry in order with `raw_copy_file`; only the index's `files` change (keys come out
      sorted). Index entries the scanner rejects or that are shadowed by a later same path are left
      out with a warning; off-allowlist links, unidentified files and case-twin paths stay, with
      warnings. Unsafe zip entries (incl. empty or `.` path components) are left out. Writes temp +
      fsync + verify + re-stamp of the source + no-replace rename (replacing only the path the dialog
      confirmed; Unix fsyncs the folder), removes the temp file on failure, and clears its own stale
      `.modpack-doctor-pack-<hex>.tmp` files older than 1 h. Nothing is downloaded.
    - Hardening (M7 review): a pack with duplicate entry names (also case-insensitive, except
      folders) is refused whole; every entry is read with local/central header consistency
      enforced (a mismatched entry is skipped with a `ScanIssue`); the end-of-central-directory
      record(s) incl. ZIP64 are checked by hand before parsing (≤ 20 000 entries, central directory
      ≤ 12 000 000 bytes). Only jars directly in `overrides/mods/`, `client-overrides/mods/`,
      `server-overrides/mods/` are scanned; other jars under the override trees are `ScanIssue`s.
      `downloads` keep every string URL ≤ 4 096 bytes (up to 64); anything else becomes a sentinel
      that is never a valid URL (`invalid:too-long`, `invalid:not-a-string`, `invalid:not-a-list`,
      `invalid:more-urls`) plus a `ScanIssue`, so W-MRPACK-DOWNLOAD always sees it. URLs of index
      entries that were skipped (bad hash, unsafe or folder path) or shadowed by a later entry with
      the same path go to `ScanResult.unverifiedDownloads` and are checked too (a launcher may still
      install them); an index over 10 000 files declares nothing but still has every entry's links
      checked this way. `mods/` matches case-insensitively in override paths. The read-only rule
      pins the canonical path captured at open; if it later resolves elsewhere the pack is unreadable
      until reopened. A `:` in a file name (alternate data stream) is never a pack or a report name.
      Pack identity overrides are refused (`Invalid`): packs are session-only. Display names strip
      control and Unicode format (bidi, zero-width) characters.
    - Also (M7, implementation limits): one override jar ≤ 256 MiB (skipped above); a drop handles
      at most 32 files; when `overrides/X` and `client-overrides/X`/`server-overrides/X` both exist,
      both are scanned and the shadowed one gets a `ScanIssue`; a pack's `modCount` = declared
      `.jar` files + override jars; an unusable index gives `metadataSource: inferred`.
16. **Reports (M7).** `src/core/report` (frozen API in its `index.ts`) builds the report from the
    same data the UI shows: instance, effective pack, scan summary, static + crash findings with
    evidence, Modrinth match summary. Markdown and JSON (`schemaVersion: 1`). No absolute paths of
    the user's home in the report: paths are shown relative to the game dir, and the game dir with
    the home folder replaced by `~` (Rust's `home_dir`; the UI's path heuristic only as a fallback),
    including its 8.3 short forms, percent-encoded and NFC/NFD variants, and UNC admin-share forms. `save_report` opens the native save dialog with the sanitized
    default name and the format's extension (`.md` / `.json`, enforced), contents ≤ 16 MiB, writes
    temp + rename in the chosen folder. An existing file is replaced only when the dialog confirmed that exact path;
    if the extension had to be appended, an existing file is a `Conflict`. That path and the fixed-pack copy (invariant 15)
    are the only writes outside PathGuard roots, allowed because the user picked them in a native
    dialog; nothing else may be written there.
17. **Interaction (M7).** Shortcuts: Ctrl/Cmd+K palette, J/K next/previous finding, Enter expand,
    Ctrl/Cmd+R rescan, Esc closes the top-most layer. Webview reload keys (F5, Ctrl/Cmd+Shift+R)
    are swallowed. Shortcuts never fire while typing in an input,
    and never execute a work order (Enter stays bound to DESIGN §6.4's rule). Context menus are
    native Tauri menus (`@tauri-apps/api/menu`, `core:menu:default`) under Tauri and a DESIGN-styled
    DOM menu in the browser dev build; every menu item that mutates files only *plans* a work order.
    The drop overlay follows Tauri's webview drag events under Tauri (DOM drag events in the browser
    build), for the visual only: opening a dropped pack is always Rust's `InstanceAdded` / `DropRejected`.

18. **Release and updates (M8).**

## Finding codes

| Code | Default severity | Meaning |
|---|---|---|
| `E-WRONG-LOADER` | error | jar targets a loader the pack doesn't run (NeoForge 1.20.1 ↔ Forge 47.x counts as compatible) |
| `E-MC-RANGE` | error | declared Minecraft range excludes the pack's MC version |
| `E-LOADER-RANGE` | error | declared loader-dependency range excludes the pack's loader version |
| `E-DEP-RANGE` | error | dependency present, but its version is outside the declared range |
| `E-MISSING-DEP` | error | required dependency absent. Built-ins count as present: `minecraft`, `java`, `forge`, `neoforge`, `fml`, `mcp`, `javafml`, `lowcodefml`, `fabricloader`, `fabric-loader`, `quilt_loader`, `quilt-loader`, plus `mixinextras` only where the loader bundles it (`src/core/checks/builtins.ts`). `fabric` is **not** built in, because that id is Fabric API. `provides` and nested jars also count as present. When a top-level jar declares the id but isn't used (disabled, damaged, another loader's build, other side), the title names that jar and the reason instead of "not installed" |
| `E-DUP-ID` | error | two active top-level jars declare the same mod id (identical nested libraries are de-duplicated) |
| `E-SPLIT-PKG` | error | same Java package in the own classes of ≥ 2 top-level jars, on Forge/NeoForge (JPMS `ResolutionException`) |
| `I-SPLIT-PKG` | info | same, on Fabric/Quilt (no module layer) |
| `E-INCOMPAT` | error (warning for Fabric `conflicts` / NeoForge `discouraged`) | a declared incompatibility entry is present and in range |
| `W-CLIENT-ON-SERVER` | warning | client-only mod in a server instance |
| `W-MRPACK-DOWNLOAD` | warning | a `.mrpack` index file lists a download URL whose host is outside Modrinth's allowlist (invariant 15) |
| `W-CORRUPT-JAR` | warning | jar unreadable or its metadata is invalid |
| `I-NOT-ON-MODRINTH` | info | hash not found on Modrinth (possibly CurseForge or manual); never raised for `failed` lookups |
| `W-JAVA-CLASS` | warning | jar's class files need a newer Java than the pack's MC version ships with |
| `C-MIXIN` … `C-SUSPECTED` | from the log | mixin, resolution, missing mandatory deps, Fabric incompatibility, NoClassDef, OOM, Java version, suspected mods |
| `C-ROOT-CAUSE` | error | fallback when nothing specific matched: the innermost `Caused by:`, mapped to a jar when possible |
| `C-NATIVE` | error | hs_err native crash; names the problematic frame and library (e.g. a GPU driver) |
| `C-JVM-START` | error | Java stopped before the game started: an unrecognised or removed JVM option, an invalid heap setting, -Xms above -Xmx, a missing main class, a boot-layer FindException, or the generic "Could not create the Java Virtual Machine" |

## Rules-core entry points (frozen in M3)

The UI calls only these from `src/core` for static checks:

| Function | File | Contract |
|---|---|---|
| `resolvePack(instance, scan, override?)` | `src/core/pack/index.ts` | → `PackContext`. Precedence: override, then launcher/mrpack metadata, then the majority across active jars. Never throws. |
| `buildJarIndex(scan)` | `src/core/pack/index.ts` | → `JarIndex` over active jars, as described on the type. |
| `runChecks(input)` / `CHECKS` | `src/core/checks/index.ts` | → `Finding[]`. Deterministic, with stable ids. Sorted by severity (error, then warning, then info), then code, then the first culprit's file name. |
| `analyzeCrash(input)` / `CRASH_ANCHORS` / `CRASH_ANCHOR_TEXTS` | `src/core/crash/index.ts` | Crash analysis (M4 wires it). |

Scan flow (M3):
1. The UI calls `scan_instance`. Rust emits `ScanStarted` and then `ScanProgress`.
2. Rust returns the `ScanResult`.
3. The UI runs `resolvePack` → `buildJarIndex` → `runChecks` synchronously. Checks are pure and fast.
4. The UI paints tile states from the findings' culprits.

Scope notes (M3): launcher root folders added with `pick_launcher_root` are **not** PathGuard
roots themselves. Only the instance roots discovered inside them are, so a Prism root's
`accounts.json` stays out of reach. The app data dir is a pinned root.
